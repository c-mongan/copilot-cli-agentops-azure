## Current project-local attach status

`agentops attach --repo .` is a read-only preview that discovers repository agents and Agent Skills, then reports counts and file hashes without copying prompt, skill, reference, or script contents. `agentops attach --repo . --yes` records that inventory in `.agentops/attachment.json` with an ownership receipt. It installs no hooks and does not activate telemetry by itself. The inventory covers supported Python, JavaScript, and TypeScript file extensions across the repository, excluding dependency/build folders. When the user explicitly launches `agentops copilot` from the attached repo, the launcher passes a run ID and OTLP endpoint to child processes and enables startup bootstraps only for unchanged, hash-matched script files. Plain `copilot`, other processes, unlisted scripts, and changed or oversized files are outside that bootstrap scope. Python uses its standard library by default, with the OTel SDK as an optional implementation; Node uses a built-in OTLP/HTTP exporter, and TypeScript support depends on the selected runtime loader. `agentops detach --repo .` previews removal; `--yes` removes only unchanged attachment files verified against the receipt and leaves other `.agentops` files alone. An attached Copilot run has now executed repo-wide Python and Node scripts and joined their OTel receipts with Copilot native spans; Azure metadata readback verified the run. Ordinary-session isolation, second-repo removal, and complete supported-script coverage remain unproved.

`agentops coverage --repo . --json` compares the current repository inventory with private local run exports explicitly associated by a one-way repository-path hash. It reports observed names and denominators for agents, skills, references, and scripts. Unobserved means only that no associated local export showed the component; it does not mean unused. Historical run exports without this association are left unassigned.

`agentops copilot` now exports session events and matching native/script spans after an opted-in run, writes owner-only files under `~/.agentops/runs/<run-id>/`, and uploads each metadata stream through the attached project's metadata DCR when configured. The receipt shows Events and Spans delivery separately. Azure API acceptance does not prove Log Analytics readback; query the run before treating it as available. Export files remain local for diagnosis when configuration or upload is incomplete. The lower-level `copilot-session export-spans <session-id> --run-id <id> --output <dir>/AgentOpsSpans_CL.jsonl` command remains available for manual inspection or re-export. `ToolCallEvidence` distinguishes an exact session event ID from an inferred script link based on a unique script-path match contained inside one Copilot native tool-span interval; ambiguous or overlapping intervals remain unlinked. This is temporal evidence, not a physical trace parent. Prompt, tool argument, and result payload attributes are omitted.

`copilot-session export-events <session-id> --run-id <id> --output <dir>` remains available for owner-only manual exports from supported Copilot session events. It preserves exact event and tool-call IDs plus a manifest-allowlisted, repository-relative reference path. It omits prompts, answers, reasoning, raw tool arguments/results, and command arguments. Use `azure-ingest --events-only` to preview or upload a manually prepared `AgentOpsEvents_CL` batch.

This is the first usable slice of the broader [requirements](requirements/full-agent-observability-requirements.md). It combines Copilot CLI's native session events with exact-session native OpenTelemetry spans from local Collector receipts to build a timed waterfall. The Azure route continues to use the existing Collector and optional `AgentOpsContent_CL` path.

## Inspect one synthetic run

```bash
node agentops-cli/src/index.js copilot-session view <session-id> \
  --output /path/to/synthetic-run.html --allow-content
```

The command reads the local `native-receipt.jsonl` and `native-azure-receipt.jsonl` files when present, or accepts repeated `--otel-file <path>` for Collector OTLP JSONL, Copilot CLI native file-exporter JSONL, and owned-script receipts. Native Copilot spans must match `gen_ai.conversation.id` or `agentops.session.id` exactly. Add `--run-id <id>` to include owned-script spans whose `agentops.run.id` matches exactly; those rows are labelled **logical run links**, not physical native child spans. When a matching local run outbox exists, the page also shows per-stream Events/Spans row counts, attempts, and delivery state. It never displays target credentials or endpoints; Azure HTTP acceptance is labelled readback-unverified. The page reports exact-session native spans, run-linked script spans, and exact tool-call ID joins separately. Receipts stay local, and this command does not upload anything. The attached Copilot CLI 1.0.89 run verified native spans plus Python protobuf and Node JSON script receipts in one waterfall, with three logical script-to-tool links and exact MCP/subagent joins.

[GitHub's Copilot CLI reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference) defines `gen_ai.conversation.id` as the session identifier and documents its native OTel model/tool spans. This view reads local Collector OTLP JSONL or Copilot file-exporter JSONL; it does not directly query Azure traces.

The output is a self-contained local HTML file created with owner-only permissions. The command refuses to overwrite an existing file. It opens with a failure detail panel: captured error, previous user message, tool arguments, and links to the full event, preceding assistant message, and exact matching native span when available. "Failure signals" can count the same operation twice when both the session event and native span report it; the panel does not infer a root cause. A no-failure result means only that no failure signal was observed in the available evidence. The run summary also counts coverage gaps from operations without observed completion or matching edges, invalid event timestamps, and uncorrelated stream deltas.

The end-to-end timeline shows elapsed position and duration for model turns, tools, hooks, and matched native OTel spans. Overlap is visible. It groups assistant token deltas into one message operation, pairs subagent start/completion into a timed interval, assigns worker events to that worker's lane, and excludes private reasoning deltas from the operation list. Omitted reasoning/background updates are counted in the page; final message content remains available only in the explicitly enabled local view. Filters show all events, failures, tools, or native spans. Click a row to see its source and fields. Exact `toolCallId` joins add known MCP server/tool identity to native spans; tool completions without names are paired to starts through `toolCallId`, and missing starts are marked.

**Synthetic UI proof (30 September 2026):** The latest isolated end-to-end fixture rendered 601 raw timeline rows before projection and 88 operation rows after grouping. It showed separate `fixture-agent` and `fixture-investigator` lanes, a 2.962-second observed subagent interval, two exact MCP server/tool spans, six tool-ID joins, and three script spans as run-ID logical links. No reasoning content appeared in the rendered page. The view still lacks a full causal trace tree, exact physical parentage for script processes, architecture-definition links, and a multi-run index. This is a tested single-run debugging view, not an enterprise-ready observability claim.

**Attached full-flow waterfall (30 September 2026):** Earlier report: session `79ca356b-83dd-4bdf-bd72-0baf51d4f153`, run `wrapper_run_33995b030d797343`, with 16 exact-session native spans and three run-linked script spans. Its Azure rows include two MCP calls, worker attribution, and script-to-shell-call edges. A later repo-wide report covers session `dff04799-4d1a-4492-9e87-8099eda6fd4b`, run `wrapper_run_74af0b4c9a7a5fa4`, and 19 native plus three Node script spans. Azure readback for the later run returned 39 metadata rows. Python scripts executed, but emitted no spans because the isolated interpreter lacked OTel packages. Process isolation, full Python coverage, and production Azure controls remain open. A further standard-library Python waterfall is saved with its session artifacts.

**Standard-library Python proof (30 September 2026):** Session `48563e27-a8f2-4a02-972a-d97523825c37`, run `wrapper_run_44883e727898e3f8`. Copilot invoked the skill-folder and repository-root Python probes through the normal `python3` command, with no OTel packages installed in that interpreter. Both emitted valid OTLP protobuf root spans and Azure returned 15 metadata rows (6 native spans, 2 Python script links, 7 span events), with canonical IDs and no failures. Each script path links to the exact bash tool call that ran both probes. This validates the standard-library fallback; it does not claim physical cross-process parent spans.

## Rich synthetic EVAL content in Azure

The user chose to test rich cloud content with synthetic agents and fixtures. The [synthetic EVAL Azure path](synthetic-eval-azure.md) now has a content producer, content-only validation/upload plan, and isolated Bicep template. The default strict Collector drops prompt, tool argument, and result content, so simply switching on the native Copilot OTel content flag would **not** make rich content reach Azure.

Cloud uploads cannot be undone by changing future redaction settings. Keep STANDARD as a separately verified metadata policy; mark EVAL/FORENSIC runs and their content explicitly. Development here uses synthetic/public content only. The [deployment plan](../.azure/deployment-plan.md) records the existing Azure resources and the template migration risk before any upload.

## MCP setup for repo users

- GitHub Copilot CLI: [`.github/mcp.json`](../.github/mcp.json) defines read-only Azure Monitor, Microsoft Learn, and Context7 for trusted repository sessions. The Azure Monitor server exposes Log Analytics KQL tools; no Azure Data Explorer cluster is required.
- Codex: [`.codex/config.toml`](../.codex/config.toml) defines the same servers for trusted project sessions.
- Context7 uses its OAuth endpoint; a client may request a browser sign-in on first use. No API key is committed.
- Always target Visual Studio Enterprise subscription `0222a208-955a-45fd-b6d8-ca4704421bf0` in Azure queries. The machine's current default subscription is Pay-As-You-Go.

The MCP files have valid JSON/TOML syntax. Active project loading and authenticated tool calls still need a fresh Copilot/Codex session verification; current global MCP listings alone do not prove project loading.
