## Existing project to continue

[c-mongan/copilot-cli-agentops-azure](https://github.com/c-mongan/copilot-cli-agentops-azure) is already an MIT-licensed implementation of the proposed Copilot-to-Collector-to-Azure/Grafana path. At inspected `main` commit `090d337d4226d7f8a3ebadc2228e9cb4c8e326b5`, it contains a Node CLI, localhost Collector configurations, strict metadata allowlists, local receipts, Copilot session enrichment, KQL, Grafana dashboards, Azure templates, and many tests. Its own [design status](https://github.com/c-mongan/copilot-cli-agentops-azure/blob/main/docs/simplified-azure-design.md) calls Azure live-pilot status unverified and says the old configured resource group is absent. This is the primary reuse target; another platform repository would duplicate it.

The current default is metadata only. [Privacy modes](https://github.com/c-mongan/copilot-cli-agentops-azure/blob/main/docs/privacy-modes.md) explicitly leave its prompt/response viewer empty under strict mode, and the strict Collector removes prompt, response, tool arguments and results. That is appropriate for the Azure route, but the user's newly confirmed **detailed local synthetic run** needs a separate local content archive/viewer. The existing native Copilot `events.jsonl` already contains those fields for the synthetic run. Use that record directly, or put a scoped viewer beside AgentOps, before designing a new capture layer.

I loaded this repository's `session-enricher.js` against only the known synthetic Copilot CLI 1.0.89 session. The input had one `tool.execution_start` with `toolName`/`arguments` and one `tool.execution_complete` with `toolCallId`/`result`/`success` but no `toolName`. The enricher output contained one `tool.call` and **zero `tool.completed`** records because its completion handler requires `data.toolName`. It also intentionally omits raw arguments and results. This is a concrete CLI schema compatibility gap to fix and test in that repository before claiming complete run reconstruction. No repository file or setting was changed by the check.

The smallest plausible arrangement is native CLI export for timing and causality plus a scoped session-history viewer for messages and tool details. AI Observer is a strong local OTel-viewer candidate; Copilot Session Tools and Project Telescope are session-history candidates. Joining the two record types is optional until a real debugging question requires it. Azure, a new Collector service, and automatic optimization are not prerequisites for the first local answer.

## What the synthetic CLI run actually retained

The installed Copilot CLI 1.0.89 wrote 21 native session events for the successful synthetic run. The event data had `content` for the user and assistant messages, `arguments` on `tool.execution_start`, `result` on `tool.execution_complete`, and model/usage/shutdown fields. This is structural inspection of that one known synthetic session; no other personal session was read. The separate OTel export contained connected agent, chat, and tool spans and metrics. With content capture off, the synthetic prompt and tool payloads were absent from that export. Native session history and OTel therefore serve different views and should be retained as two source types in the first pilot.

The Microsoft Azure guide labels the Collector and its Azure Monitor exporter as community-supported components, while Azure Support covers the Azure services. The guide documents a Collector-to-Application Insights path and also points to separate native OTLP ingestion. [Microsoft's July 2026 change log](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/whats-new) says native OTLP ingestion through an OpenTelemetry Collector reached general availability; the broader [OTLP options overview](https://learn.microsoft.com/en-us/azure/azure-monitor/containers/opentelemetry-summary) still carries preview wording for other paths. These routes do not prove that rich CLI session records arrive in the Agents view unchanged. [Copilot CLI's official OTel controls](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference#opentelemetry-monitoring) provide the producer contract to check against either route.

## Cross-check of the additional pasted research

The pasted summary is useful and largely consistent with current primary sources. [GitHub's CLI reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference#opentelemetry-monitoring) confirms `invoke_agent`, `chat`, and `execute_tool` spans, and that content capture is off by default. [GitHub's July 2026 changelog](https://github.blog/changelog/2026-07-08-enterprise-managed-opentelemetry-export-for-vs-code-and-cli/) and [managed-settings reference](https://docs.github.com/en/copilot/reference/enterprise-administrators/enterprise-managed-settings#telemetry) confirm the enterprise `telemetry` block for CLI and VS Code. [GitHub's hooks reference](https://docs.github.com/en/copilot/reference/hooks-reference) confirms the listed extension points.

Three qualifications matter for this project: (1) native OTel is the timing/telemetry source, while native session events are the richer local record of the exact trajectory; (2) hooks can emit additional records, but automatic parent/trace linkage to CLI spans was not demonstrated, so the claim that they join "the same pipeline" is an implementation proposal; (3) Microsoft's coding-agent Azure guide configures VS Code for Copilot, so a Copilot CLI-to-Azure path still needs its own end-to-end compatibility check. The pasted `:chatgpt-content-reference` markers do not resolve to sources, so the linked primary documentation above is the evidence.

**Decision:** use a synthetic-only local session-history viewer first, keep the CLI's OTel export for timing and correlation, and trial Azure ingestion later with an explicit content policy. Rich prompt and tool content can remain in the local synthetic archive. Do not enable a cloud exporter for it merely to obtain a dashboard.
