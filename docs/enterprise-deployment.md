# Additive enterprise qualification deployment

This entry point adds a saved Azure Workbook to the existing synthetic pilot. It does not create, replace, reconfigure or rebind Log Analytics, tables, DCR, DCE or Application Insights. It does not deploy Grafana, AKS, an application host, storage, a judge, a private endpoint or a paid network service. No cloud deployment is implied by local compilation.

```text
Existing metadata DCR + DCE -> existing LAW tables -> saved Workbook
Approved publishers          approved table readers  observers / editors
```

Use `infra/bicep/enterprise-existing-workspace.bicep`, not `main.bicep`, `observability-views.bicep` or `azd provision`. The latter paths can create resources, rebind Application Insights, or run postprovision imports. The dedicated entry point references all existing resources in the explicitly selected subscription and resource group; cross-resource-group references are not supported by this baseline.

1. Copy `enterprise-existing-workspace.parameters.example.json` to an ignored local parameters file. Verify all four existing resource names, North Europe location, workspace/DCR/DCE region agreement, DCR destinations and eleven metadata streams. Replace the DCE placeholder from actual resource readback. The example date is illustrative; verify the first day of the approved budget month. No secret or connection string belongs in this file.
2. Run `node scripts/check-enterprise-iac.js`. It uses the already installed `~/.azure/bin/bicep`, or the absolute executable in `BICEP_CLI`. It compiles locally and checks the resulting ARM deployment contract. It never downloads a compiler or calls Azure.
3. Before any cloud write, obtain target-bound validation and what-if using the explicit subscription/resource group and final parameters. Review only Workbook, optional budget/action group/disabled rule, scoped role assignments and nested deployment changes. Reject LAW/table/DCR/DCE/component changes. Compilation does not prove provider availability, policy compliance, budget eligibility, permission sufficiency or live query execution.
4. Deploy only after the concrete target, contacts, access, currency/amount, inherited permissions and additive what-if are approved. Use incremental mode. Read back the saved Workbook and unchanged App Insights workspace binding, ingestion endpoint/immutable ID, budget and any assignments. Exercise the rendered Workbook and allowed/denied queries as actual observer/editor/publisher identities.

The required parameters are `workspaceName`, `metadataDcrName`, `dataCollectionEndpointName`, `applicationInsightsName`, and `location`. Workbook ARM name defaults to `guid(resourceGroup().id, workspaceName, 'agentops-diagnostic-pilot')`; its visible name defaults to `AgentOps Diagnostic Pilot`. The module embeds `workbooks/agentops-enterprise-workbook.json` at compile time and binds `sourceId` to the selected LAW ARM ID. At deployment it also binds the single Workspace parameter's value explicitly to that ARM ID, and sets serialized root `fallbackResourceIds` and `defaultResourceIds` to the same one-element array. Other parameters and query items are preserved. This avoids relying on implicit portal context when the saved Workbook is opened from Azure Monitor; the earlier implicit default rendered with no resource selected. The reusable asset keeps Microsoft's current-resource option, but deployed JSON has an explicit selection. Local checks validate the actual compiled transformation; rendered selection and query execution remain portal acceptance gates.

Access inputs are four separate arrays: `observers`, `editors`, `publishers`, and `metadataReaders`. Each element must be `{ "objectId": "<approved immutable Entra object GUID>", "principalType": "Group" }`, with `Group`, `ServicePrincipal`, or `User` explicitly selected. All default empty. Include query users explicitly in `metadataReaders`; Workbook access alone does not grant data access. Verify IDs, types and duplicate entries before validation. No group is created and no display name is used as an identity target.

| Input | Role | Exact scope |
| --- | --- | --- |
| observers | Workbook Reader `b279062a-9be3-42a0-92ae-8b3cf002ec4d` | Saved Workbook |
| editors | Workbook Contributor `e8ddcd69-c73f-4f9f-9844-4100522f16ad` | Saved Workbook; includes deletion permission |
| metadataReaders | Log Analytics Data Reader `3b03c2da-16b3-4a49-8834-0f8130efdd3b` | Selected workspace; mandatory condition limits data to eleven fixed metadata tables |
| publishers | Monitoring Metrics Publisher `3913510d-42f4-4e42-8a64-420c390055eb` | Existing metadata DCR only |

Role GUIDs were checked against [Microsoft's built-in Monitor roles](https://learn.microsoft.com/en-us/azure/role-based-access-control/built-in-roles/monitor). Verify effective definitions at the selected tenant before assignment. Assignments are deterministic, additive, independent of Grafana, and contain no Owner/Contributor, subscription Reader, unconditional workspace data grant or content grant. They do not remove inherited permissions. A metadata publisher can write every stream accepted by the specified DCR, so reject any DCR that includes a content route.

Readers use Microsoft's recommended [workspace-scoped granular RBAC](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/granular-rbac-log-analytics). A table-scoped Data Reader grant alone does not supply the parent workspace's query/read or portal navigation permissions. One workspace-scoped assignment per principal supplies those control permissions while its data action has a mandatory restrictive condition. No custom role or extra service is created. The assignment has `conditionVersion: '2.0'` and this exact condition:

```text
(
  !(ActionMatches{'Microsoft.OperationalInsights/workspaces/tables/data/read'})
  OR
  @Resource[Microsoft.OperationalInsights/workspaces/tables:name] ForAllOfAnyValues:StringEquals {'AgentOpsRunSummary_CL', 'AgentOpsEvents_CL', 'AgentOpsSpans_CL', 'AgentOpsToolCalls_CL', 'AgentOpsMcpCalls_CL', 'AgentOpsPrivacy_CL', 'AgentOpsEval_CL', 'AgentOpsGithubOutcomes_CL', 'AgentOpsInsights_CL', 'AgentOpsRecommendations_CL', 'AgentOpsCollectorHealth_CL'}
)
```

The action guard and resource-name grammar follow the [official restrictive example](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/granular-rbac-use-case); the membership operator is documented in [granular RBAC expression operators](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/granular-rbac-log-analytics#expression-operators). The fixed case-sensitive allowlist excludes content and newly added tables. Other role actions remain permitted; this condition restricts the table data action.

Before nonempty reader assignments are deployed, inspect inherited/group permissions and workspace access mode. Resource-context enforcement requires `Require workspace permissions`; this template does not modify that setting. Existing broader Reader/Contributor/Owner access can bypass the data restriction. Qualified content denial requires an approved test identity without any broader grants, successful queries across all eleven allowed tables and the rendered Workbook, and failed/empty content-table queries through both workspace and resource contexts. Owner-based tests cannot prove this boundary. Allow propagation time and inspect effective conditions. Local contract checks prove the generated condition and membership, not Azure authorization. These requirements follow [Microsoft's table-access guidance](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/manage-table-access) and [granular RBAC considerations](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/granular-rbac-log-analytics#frequently-asked-questions).

Run `node scripts/check-enterprise-access.js <parameters.json> <workspace-arm-snapshot.json> <subscription-id> <resource-group>` before validation/deployment, using a fresh ARM workspace GET snapshot with `id` and `properties.features`. The guard binds that snapshot to the exact target, validates explicit principal types/GUIDs and rejects nonempty `metadataReaders` unless `enableLogAccessUsingOnlyResourcePermissions` is exactly false. A missing field is insufficient evidence. Empty owner-only qualification is permitted but never reported as team access proof. Run its four local failure/success tests with `node --test scripts/check-enterprise-access.test.js`. The guard performs no Azure call or workspace-setting update; invoking ARM directly bypasses it, so the deployment owner must invoke it as a required preflight. If current feature readback is true, first prepare and review a separate narrow access-mode update with prior configuration snapshot and recovery; do not silently deploy team grants or overwrite the workspace with a full resource template.

`deployBudget` defaults false. When approved, set it true, `monthlyBudgetAmount` in verified billing currency (default proposed amount 10), and `budgetStartDate` to a valid first-of-month UTC date. `budgetContactEmails` defaults empty; an empty list creates no notifications. Approved contacts enable actual 80%, actual 100%, and forecast 100% email notifications. The RG budget covers the entire selected RG, not just the new Workbook, and is not a hard cap or proof that credits or Copilot overage are protected. An unrelated RG/subscription is outside its scope. Its API is `Microsoft.Consumption/budgets@2024-08-01`.

`deployActionGroup` defaults false and also requires nonempty `actionGroupContactEmails`. If created, the email-only action group remains disabled. `deployHealthRule` defaults false; the optional 15-minute rule always remains disabled. It detects explicitly unhealthy collector receipts and cannot detect silent ingestion loss or prove health from absence of rows. There is no alert/action-group enable switch in this baseline. Synthetic fault, scheduled-publish heartbeat, notification and cost qualification require a separate reviewed change before enabling either resource. No contacts are invented and local checks send no notifications.

Recovery preserves cloud evidence. Stop the publisher, remove only newly approved publisher grants if containment requires it, disable any later-enabled rule/action group, and restore the exported prior Workbook JSON and configuration. Capture prior nonsecret Workbook/budget/access configuration before writes; do not delete the workspace, tables, existing DCR/DCE, component, inherited grants or resource group. A Workbook name collision updates that deterministic existing Workbook, so inspect prior state first. RBAC revocation, notification enablement and budget updates are separate external mutations requiring target authorization. Private data onboarding, production deployment and paid service expansion remain outside synthetic qualification.
